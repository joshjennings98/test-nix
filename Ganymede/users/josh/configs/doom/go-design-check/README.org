#+title: Go design check

The deterministic Go analyser for this Doom Org review workflow. Emacs owns the
backing document, baseline worktrees, agent reviews and Magit navigation. This
tool validates proposed declarations and checks explicit structural requirements.
It does not author documents, run tests or manage approval state.

The type-aware loader and SSA/VTA call analysis were adapted from designlint.
Proposal parsing and type checking preserve the distinction between a valid
unimplemented plan and an implementation that satisfies it.

* Build and test

Requires Go 1.26 or later, with the Go command on PATH during analysis.

#+begin_src sh
go build -o bin/go-design-check ./cmd/go-design-check
go test ./...
go vet ./...
bin/go-design-check check --root testdata/service --request examples/check.json
#+end_src

Use =-buildvcs=false= when building without usable Git metadata.

* Editor protocol

=validate= reads the structured graph document from stdin (or =--request FILE=),
checks its declarations and baseline relationships, and returns compiled check
requests keyed by graph ID. Proposed additions need not exist yet. Emacs calls it
against the pinned baseline when validating an Org document.

=check= reads a compiled request against the current implementation. For example:

#+begin_src json
{"rules":[{"id":"save-path","kind":"reaches","from":"example.com/service.Create","to":"example.com/service.Save"}]}
#+end_src

Findings include IDs, PASS/FAIL/UNKNOWN status, explanations, witness paths,
source locations and relevant analysis gaps. Locations are relative to =--root=,
with one-based lines and columns. Requests must contain unique non-empty IDs;
unknown fields, unsupported kinds, empty checks and trailing JSON are rejected.

| Kind              | Required fields   | Meaning                           |
|-------------------+-------------------+-----------------------------------|
| exists            | symbol            | Declaration exists                |
| absent            | symbol            | Declaration is absent in scope    |
| signature         | symbol, signature | Exact canonical declaration shape |
| direct_call       | from, to          | A definite direct call exists     |
| reaches           | from, to          | A definite call path exists       |
| forbid_call       | from, to          | No direct call exists             |
| forbid_path       | from, to          | No call path exists               |
| implements        | from, to          | Go method-set conformance         |
| forbid_implements | from, to          | Method-set conformance is absent  |
| member            | from, to          | Type contains the member          |
| forbid_member     | from, to          | Member relationship is absent     |

Use full module/package-qualified identifiers from source inspection. Examples:

#+begin_example
example.com/app/service.Create
example.com/app/service.(*Service).Create
example.com/app/model.(Record).Name
*example.com/app/service.Service    (pointer type in an implements rule)
#+end_example

The proposal validator compiles canonical signatures for =check=. There is no
fuzzy name resolution. Missing required symbols produce FAIL; incomplete analysis
produces UNKNOWN. A missing caller also fails a negative relationship requirement.
Call-graph connectivity does not establish runtime ordering; focused agent review
and tests assess that separately.

* Scope and environment

=--root= selects a Go module/workspace. =--packages= accepts comma-separated Go
patterns (default =./...=). Dependencies provide type information; their bodies
remain outside the analysed scope. Unrelated nested modules are not discovered.

=--tags=, =--goos=, =--goarch= and =--cgo auto|on|off= select the build variant.
OS/architecture default to the host; auto CGO inherits the Go environment.
The package loader inherits the environment with those explicit overrides and
=GOPACKAGESDRIVER=off=. It can invoke Go and download dependencies according to
normal Go configuration. There is no separate build-metadata subprocess.
=--timeout= bounds the analysis context (default two minutes).

Only production packages are analysed. Tests are excluded. Interface dispatch,
callbacks, reflection, unsafe operations and missing bodies can leave uncertainty.
Possible paths do not satisfy definite-call requirements or prove absence.
Package-loading failures prevent clean structural verdicts; an unrelated call
gap need not invalidate a focused check.

Exit codes: 0 PASS, 3 FAIL, 4 UNKNOWN, 5 invalid input or tool error. FAIL takes
precedence over UNKNOWN across findings. Use the built executable because =go run=
does not preserve its exit codes. Reruns after edits are explicit; there is no
snapshot comparison, source watcher or automatic freshness guarantee.
