#+title: Org design review

* Plan across languages

The workflow uses one Org document and separate Agent Shell review conversations per block.
Elisp validates document structure and unique IDs. No Go tool or compiler is needed.

Use =review-create= to pin a Git baseline, =review-read= to read the live document,
and =review-set-plan= with =path=, =id= and =body= to add or refine a freeform box.
Separate distinct parts such as frontend, backend and configuration into their own
named boxes. Choose component trees, call-tree diffs, signatures, pseudocode, file
trees, diagrams or prose according to the feature. There is no call-graph grammar.
Make current behaviour, proposed changes and preserved behaviour clear.

=review-set-context= places rationale or renderable diagrams beside a box.
=review-set-tests= retains one named test and its expectations per test-review box.
Source delimiters cannot be nested inside review bodies. Bodies are never run as
application code; Babel dispatches them to the reviewer.

* Review

=validate-document= checks structure only. =review-check= queues reviews for one
ID or the whole document. =review-results= returns progress and result drawers.
Each focused plan reviewer receives only its complete assigned specification.
It must not import requirements from other boxes. The implementor and overall
reviewers receive the full document. It must inspect actual code/configuration and give evidence for
additions, changes, removals and preserved behaviour, regardless of language or
notation. Each plan review also shows a multiline Show Me comparison of the plan
with the observed implementation, alongside findings and source links. It can use
an annotated tree, pseudocode diff, configuration comparison or labelled views.
It distinguishes missing work, deviations, equivalent implementation and uncertainty.
Matching context stays visible; aligned work shows the checked structure with no
differences reported. Missing evidence or an omitted comparison is UNKNOWN.

The overall implementation reviewer assesses integration, edge cases and shared
context. Non-test reviews run concurrently. Test reviewers assess expectations only after
all non-test assessments pass for the same snapshot. Diagram reviewers assess rendered-diagram intent; change
reviewers identify work outside the plan. Agent judgements are advisory and are
separate from actual test execution. Results include source/diff navigation.

Freshness uses saved Git-listed files and authored requirements. Ignored files and
external dependencies are outside the snapshot. Edits invalidate evidence; rerun
reviews after changes. Late answers do not overwrite edited or removed boxes.

* Existing documents

Legacy =design-graph= boxes are interpreted as freeform plans and reviewed by an
agent, without invoking the removed Go tool. Old deterministic results are only
historical evidence. Convert a box with =review-set-plan= using the same ID and
preserved body; this clears that box's old result. Multiple legacy boxes can be
converted independently. Reconnect the Emacs navigation MCP connection after
loading the updated configuration to discover =review-set-plan=.

* Readable feature specifications

Each box contains the full approved contract for one coherent change, including
interfaces, failure behaviour and preserved behaviour. A short human summary
sits above it; results appear below. Split distinct responsibilities into separate
boxes. Within each box, use short =@@ Label= sections and blank lines rather than
long prose. Trees, signatures and pseudocode can share a box when each adds value.

Leading =+= lines are green and =-= lines red. Whitespace-separated =//= and =#=
annotations are muted, including on changed lines. ===marked text=== has a highlighter
background. These are presentation conventions, not an executable grammar.
